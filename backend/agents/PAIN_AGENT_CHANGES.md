# Pain & Symptoms Agent — proactive / memory-aware rework

Branch `feature/agents-proactive`. "Before" is `b8f0cc5` (see
`AGENTS_BASELINE.md`); every transcript below was generated by running the
real agent with a stubbed, empty LLM reply (so the deterministic close is
shown) against an isolated temp database.

Scope that was changed: `agents/pain_logic.py`, `agents/pain_integration.py`,
`agents/pain_state.py`, `PainSymptomsAgent` in `agents/specialized_agents.py`,
`test_pain_symptoms_agent.py`, and the new `agents/patient_memory.py`.
Nothing else was edited: not the orchestrator, triage, `chat_agent.py`,
`agent_router.py`, the database schema, the coordinator, or any other agent.

**Safety rule kept:** the LLM never sets or lowers the triage level. The
level and its action protocol still come from `SafetyTriageEngine` upstream,
`precomputed_triage` is still copied onto the final response unconditionally,
and the new memory/procedure logic only decides which **questions** to ask.

---

## 1. What changed and why

### 1a. Non-numeric pain-score answer → clarifying re-ask (bug)

**Before:** a reply like "it really hurts" (or "yes") to "how bad is the pain
right now?" left `pain_score` unresolved, and the acknowledgement template
was filled with the missing value: *"Okay, None pain -- that helps me
understand how strong it is."* followed by the same question verbatim.

**After:** `pain_logic.answer_plausibly_fits()` checks whether a reply fits
the pending question at all. A non-numeric, non-category reply to the score
question is never stored; the agent asks the field's `CLARIFY_QUESTIONS`
wording once ("Sorry, I didn't catch a number there. Would you put it roughly
in the mild range (1-3) ..."), and a second miss records `"unknown"`. No
template is ever filled with an unresolved value any more: the lead never
names the value; the reflection line states only what *is* collected.

### 1b. Replies that don't answer the question are never stored (bug)

**Before:** `_attribute_pending_answer()` fell back to the raw text for most
fields, so "Can I shower tomorrow?" became the stored `onset`, and in the THA
transcript below "in the groin" was stored as the *trend*.

**After:** per-field plausibility (parser match, yes/no for yes/no fields, a
number where a number is expected, location/onset/trend vocabulary, and an
off-topic-question detector). A reply that doesn't fit is clarified once via
`CLARIFY_QUESTIONS`, then recorded as `"unknown"`. Every `CLARIFY` text
deliberately contains its field's `_ALT_MARKERS` phrase, so it is recognised
as the field's *second* ask and the existing "second miss → unknown" rule
applies unchanged. Facts the reply volunteered for *other* fields are still
captured (see §3).

### 1c. Resuming after a detour (bug)

**Before:** `handle()` used the strict continuation check (the literal most
recent assistant message must be the pending Pain question). After "Can I
climb stairs?" (answered by Daily Activity) a bare "8" was routed back to
Pain by the orchestrator's bridging `_has_active_pain_followup`, but
`handle()` treated it as a fresh assessment, reset the boundary and the
cached facts, and re-asked everything.

**After:** `pain_logic.is_active_assessment_continuation(history,
pending_field, user_message=None)` keeps the strict behaviour when called
without a message (the orchestrator's cumulative-safety call is unchanged),
and when `handle()` passes the current message it tolerates intervening
turns the same way the orchestrator does: bridging `previous_pending_field`
must still point at the pending field **and** the message must not read as a
brand-new pain complaint (`looks_like_new_complaint`). So "8" resumes;
"My hip has started aching today." still starts fresh (test 29 still guards
that). `_extract_answer_pairs` also skips detour turns (a user message whose
next assistant reply is not a Pain question) for both attribution and
opportunistic extraction, so the pending question stays open across the
detour and a wound/activity message never seeds Pain facts.

### 2. Memory before asking (`agents/patient_memory.py`)

New module wrapping the existing `patient_database.py` functions, no schema
change: `load_patient_memory()` reads today's `metrics` row, the last three
`symptom_assessments`, the procedure (via `resolve_procedure_code` on the
recorded `surgery_type`) and `weight_bearing_status`; `write_today_metrics()`
updates today's `metrics` row in place or inserts one; `write_symptom_assessment()`
wraps `save_symptom_assessment`. Everything is best-effort (an unknown
patient yields an empty memory and `False` on writes, never an exception).

The agent loads memory **once per interview** (cached on `PainSessionState`,
cleared with every reset) and:

- if today's `metrics.pain_score` exists, **confirms** it instead of asking:
  *"Your log says 6/10 earlier today -- still about that?"* — "yes" keeps the
  logged value, a number overrides it, "no"/anything else falls back to the
  normal question (and never produces a "None" acknowledgement);
- if a previous assessment exists, the **opening line references it**:
  *"Last time you had 7/10 behind the knee and it was getting worse -- let's
  see where things are now."*;
- **procedure-aware wording:** a THA patient's location question offers
  groin, thigh, buttock and calf; TKA keeps the knee wording (`QUESTIONS_THA`,
  `ALT_QUESTIONS_THA`, `CLARIFY_QUESTIONS_THA`, `question_text()`). For a THA
  patient the operated joint's bare name ("my hip") is no longer treated as a
  pinpointed location by opportunistic extraction, exactly as a bare "knee"
  already wasn't for TKA, so the location question is actually asked;
- **THA branch** in `select_next_field(..., procedure=)`: calf branch shared
  by every procedure; a THA-only thigh branch (swelling → warmth, + trend when
  moderate/severe); hip-joint branch (trend when moderate/severe, + stiffness
  and numbness/weakness when severe). Collection only — triage is upstream.

### 3. Multi-slot extraction

"7 out of 10, started suddenly yesterday in the calf" fills score, onset and
location in one turn and the agent asks only what is still missing
(swelling, calf branch). This is the existing opportunistic pass, now
guaranteed not to be undone by attribution: when the pending question goes
unanswered the pending field is clarified, but the volunteered facts for
other fields are kept. One tracked question per turn is unchanged.

### 4. Progress feedback

Every mid-interview reply is: one-line reflection of what is collected +
the next question + a short indicator, under three sentences:

> Got it -- so far: 7/10, sudden onset, in the calf. Have you noticed any
> swelling in that area? (a few more questions)

The indicator comes from `pain_logic.estimate_remaining_questions()` (a
replay of `select_next_field` with neutral placeholders, i.e. a lower bound);
while a branch-deciding field (score, location) is open it stays at "(one or
two more questions)". The acknowledgement pools lost their trailing periods
and the two-sentence opening lines became one sentence so the whole reply
stays under three sentences.

### 5. Proactive close

Both final paths (accepted LLM body, or the deterministic fallback) end the
same way: summary → *Compared with last time:* (score **and**
location/trend, `build_trend_note`) → the deterministic triage action
protocol **verbatim** → exactly one *Next step:* (YELLOW/RED: the protocol's
own first sentence; GREEN: "note how the pain feels again this evening";
no protocol: "let your surgical team know if anything changes") → *"Say
'pain check' any time and I'll compare with today."* ("pain check" routes
to the Pain agent — test 53.) The LLM path opens with *"Here's what you told
me: ..."* so the summary never depends on the model. The grounding and
consistency checks still run on the LLM body alone, so they are not
weakened by the appended text.

Persistence happens only at the close: the `symptom_assessments` row as
before **and** today's `metrics` pain_score/swelling/triage via
`patient_memory.write_today_metrics()` (numeric scores only; a category or
"unknown" score never fabricates a number). Abandoned interviews persist
nothing (test 49).

### 6. Final-turn prompt

- The RAG query is built from the **collected** location and symptoms
  (`build_retrieval_query(assessment, surgery_type=, procedure=,
  postop_day=)`), e.g. *"What should I know about severe sudden-onset pain in
  the calf with swelling after Total Knee Arthroplasty (TKA) on day 7, and
  what should I do? calf swelling warmth postoperative deep vein thrombosis
  risk signs"*. `ChatAgent` uses `user_message` as both the retrieval query
  and the prompt's "User's Question", so that short text is what is sent;
  the instruction block, the fenced assessment/trend data, the patient's
  **latest raw message** (fenced) and the weight-bearing record context
  (fenced) all travel in `domain_instruction`. Test 31 was updated for this:
  injected text must now be *absent* from `user_message` and present only
  inside the fence in `domain_instruction`.
- Appended verbatim to the domain instruction:
  *"Whenever the discharge notes do not cover the question, say you don't
  have that information and ask the patient to check with their surgeon or
  physiotherapist."*
- The instruction also tells the model the system appends the protocol and
  next step itself, so it should explain findings rather than restate or
  soften the protocol.
- **Token budget:** `ChatAgent.answer_question()` exposes no budget
  parameter (`num_predict` is hard-coded inside `chat_agent.py`), so nothing
  was passed and `chat_agent.py` was not edited — see "shared changes
  needed".

### 7. Tests

`run_agent_tests.py` (new) runs the three agent suites under pytest with a
fresh temp `PATIENT_DATABASE_PATH` and every `*SMTP*` / `*DOCTOR_ALERT*`
variable cleared. In all three suites `_check()` now raises
`AssertionError` (so pytest reports real failures) while `main()` wraps each
test so the script runners still run everything and print a summary.

| Run | Collected | Passed | Failed |
|---|---|---|---|
| Baseline (b8f0cc5, after the `_check` fix) | 66 | 65 | 1 |
| After this rework | 80 | 79 | 1 |

The one failure is the pre-existing environment case
`test_recovery_progress_agent.py::test_real_keyword_fallback_retrieval`
(chromadb is installed, so retrieval takes `semantic_chroma`). Note the
baseline document's headline "66 passed, 1 failed (67 tests)" is off by one;
its own per-file table sums to 65 passed of 66.

Existing tests updated with a comment: test 8 (`ALT` is now *contained* in
the reply because of the progress indicator) and test 31 (fencing moved
from `user_message` to `domain_instruction`). New tests 40–53 cover items
1a, 1b, 1c, memory confirm, memory opening/close comparison, THA wording and
branch, multi-slot, progress shape, proactive close + persistence,
abandoned interview, RAG query + abstention sentence, CLARIFY wording,
`patient_memory` round trip, and "pain check" routing.
`test_symptom_assessment_agent.py` (out of scope) still passes unchanged.

## 2. Example conversations

### TKA calf case

Patient on record: previous assessment 7/10 behind the knee, getting worse;
today's log 6/10. Triage for the turn: YELLOW.

#### Before

**Patient:** My knee has been hurting since this morning.

> Thanks for telling me. I'd like to understand this a little better. On a scale from 0 to 10, how bad is the pain right now?

**Patient:** yes

> Okay, None pain -- that helps me understand how strong it is. On a scale from 0 to 10, how bad is the pain right now?

**Patient:** it really hurts

> Okay, None pain -- that helps me understand how strong it is. On a scale from 0 to 10, how bad is the pain right now?

**Patient:** 7 out of 10, started suddenly yesterday in the calf

> Okay, 7 out of 10 -- that helps me understand how strong the pain is. Have you noticed any swelling in that area?

**Patient:** yes it's swollen

> Thanks, that's useful to know. Does the area feel warmer than usual, or look red?

**Patient:** no

> Thanks, that's useful to know. Any numbness or weakness in that leg?

**Patient:** no

> Thanks, that's useful to know. Have you felt feverish at all, or checked your temperature?

**Patient:** no fever

> Thanks for going through that with me. Based on what you've told me:
> - pain score: 7/10
> - how it started: sudden
> - where it's felt: in the calf
> - swelling: yes it's swollen
> - warmth or redness: no
> - numbness or weakness: no
> - fever/temperature: no fever
>
> Because the safety triage result is YELLOW: Contact the orthopedic nursing hotline or schedule same-day follow-up. Elevate limb, apply cold therapy (20 mins per session), and closely monitor wound. That's the same as the pain score of 7/10 recorded last time.
>
> This is a preliminary read based on what you've described and isn't a diagnosis.

#### After

**Patient:** My knee has been hurting since this morning.

> Last time you had 7/10 behind the knee and it was getting worse -- let's see where things are now. Your log says 6/10 earlier today -- still about that? (one or two more questions)

**Patient:** yes

> Okay, that helps me understand how strong it is -- so far: 6/10. Did it come on suddenly, or has it been building up gradually? (one or two more questions)

**Patient:** it really hurts

> So far: 6/10. Sorry, I didn't quite catch that. Would you say the pain started all at once, or built up gradually? (one or two more questions)

**Patient:** 7 out of 10, started suddenly yesterday in the calf

> Got it -- so far: 7/10, sudden onset, in the calf. Have you noticed any swelling in that area? (a few more questions)

**Patient:** yes it's swollen

> Thanks, that's useful to know -- so far: 7/10, sudden onset, in the calf, swelling: yes. Does the area feel warmer than usual, or look red? (one or two more questions)

**Patient:** no

> Thanks, that's useful to know -- so far: 7/10, sudden onset, in the calf, swelling: yes, warmth/redness: no. Any numbness or weakness in that leg? (one more question after this)

**Patient:** no

> Thanks, that's useful to know -- so far: 7/10, sudden onset, in the calf, swelling: yes, warmth/redness: no, numbness/weakness: no. Have you felt feverish at all, or checked your temperature? (last question)

**Patient:** no fever

> Thanks for going through that with me. Based on what you've told me:
> - pain score: 7/10
> - how it started: sudden
> - where it's felt: in the calf
> - swelling: yes it's swollen
> - warmth or redness: no
> - numbness or weakness: no
> - fever/temperature: no fever
> 
> Compared with last time: That's the same as the pain score of 7/10 recorded last time. Last time it was behind the knee and getting worse; now it's in the calf.
> 
> Because the safety triage result is YELLOW: Contact the orthopedic nursing hotline or schedule same-day follow-up. Elevate limb, apply cold therapy (20 mins per session), and closely monitor wound.
> 
> Next step: contact the orthopedic nursing hotline or schedule same-day follow-up. Say 'pain check' any time and I'll compare with today.
> 
> This is a preliminary read based on what you've described and isn't a diagnosis.

(The "7 out of 10" in turn four is a later correction of the confirmed 6 —
the most recent number always wins, as before.)

## 3. Shared changes needed (outside this branch's scope)

1. **`agents/chat_agent.py` — token budget for the final turn.** Add an
   optional parameter and use it for `num_predict`:
   `answer_question(..., max_tokens: Optional[int] = None)` →
   `_query_llama(..., max_tokens=max_tokens)` →
   `"num_predict": max_tokens or (220 if final_wound_assessment else 150)`.
   The Pain agent would then pass `max_tokens=300` on its final
   `ChatAgent.answer_question()` call (the call site is marked with a
   `TOKEN BUDGET` comment in `PainSymptomsAgent.handle`).
2. **`lam/orchestrator.py` — cumulative safety after a detour.** The
   cumulative-safety step calls
   `pain_logic.is_active_assessment_continuation(history, pending_field)`
   without the message, so after a detour it still treats the resumed turn
   as fresh and evaluates only the current message. Passing `user_message`
   as the third argument makes it agree with `handle()` so the accumulated
   facts are triaged on that turn too. No safety regression today (before
   this rework the turn restarted entirely); it is a missed opportunity for
   one turn.
3. **`patient_database.py` — a first-class metrics upsert.**
   `patient_memory.write_today_metrics()` writes the `metrics` table through
   the existing `connection_scope()` with its own SQL because no helper
   exists. A `upsert_daily_metrics(patient_id, date, **columns)` helper there
   would be the proper home. Also: `metrics.swelling` now receives the
   patient's own wording ("yes"/"no"/free text) next to the seeded
   "Mild"/"Moderate" descriptors — anything reporting on that column
   (report agent, dashboard) should tolerate both.
4. **`symptom_assessments` has no `medication_effect` column** — still
   collected, still not persisted (unchanged from the baseline).
5. **Intent classifier:** the check-in offer depends on "pain check" being
   classified as `pain_symptoms` (verified by test 53). Keep "pain" in the
   Pain keyword set if the classifier is retuned.
6. **`AGENTS_BASELINE.md`:** the headline count "66 passed, 1 failed (67
   tests)" should read 65 passed, 1 failed, 66 tests.
