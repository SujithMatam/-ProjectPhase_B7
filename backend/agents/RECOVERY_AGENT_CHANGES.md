# Recovery Progress Agent — memory-aware, milestone-driven rework

Branch `feature/agents-proactive`. "Before" is `44bda66` (the Pain rework plus
the setup fixes; the Recovery agent itself was unchanged since the baseline in
`AGENTS_BASELINE.md`). Every transcript below was generated by running the
real agent with a stubbed, empty LLM reply against an isolated temp database,
using the same six-/five-message scripts for both versions.

Scope that was changed: `agents/recovery_logic.py`,
`agents/recovery_integration.py`, `agents/recovery_state.py`, the
`RecoveryProgressAgent` class in `agents/specialized_agents.py`,
`agents/patient_memory.py` (extended), `test_recovery_progress_agent.py`, and
the new data file `agents/data/recovery_milestones.json`. Nothing else was
edited: not the orchestrator, triage, `chat_agent.py`, `agent_router.py`, the
database schema, the coordinator, or any other agent class.

**Safety rule kept:** the LLM never sets or lowers the triage level.
`precomputed_triage` is copied onto every reply (ask turns and the final
turn), including when an LLM explanation is accepted; the LLM text can only
ever be an explanation placed *above* the deterministic comparison block,
and it is dropped if it is empty, generic, uses trajectory language or names
a number that is not in the deterministic data.

## 1. What changed and why

### 1a. Milestone data file (`agents/data/recovery_milestones.json`)

**Before:** one hard-coded checkpoint (`MILESTONE_TABLE`: TKA-03, day 7,
flexion 70–90°, extension 0–5°), applicable only inside TKA-03's own
"1-21" day window and only when the RAG retrieval of the turn happened to
return TKA-03 itself. THA and GEN had no rows and skipped the loop.

**After:** 66 entries for TKA and THA at checkpoint days 7, 14, 21, 42, 84
plus a long-term entry per procedure. Metrics: flexion, extension, walking
aid, walking duration, stairs, daily activities, driving, return to work (and
hip precautions for THA). Every entry carries the passage id, the passage's
own `source_url`, a short verbatim `quote`, and either a numeric range
(`range_low`/`range_high`, either end may be open), a categorical
`accepted_values` list, or — where the passage gives no number — an
`expected_state` in words only (`kind: "state"`). Built only from
`EV-TKA-REC-*`, `EV-THA-REC-*`, `EV-TKA-REHAB-02/03` and `EV-THA-REHAB-04` in
`eval/eval_corpus.json`, plus the two retained TKA-03 day-7 ROM entries from
`rag/data/seed_knowledge.json` so the existing tests keep their source.

`recovery_logic.parse_milestone_file()` validates the file (required keys,
known procedures/metrics/kinds, checkpoint days, numeric entries need a unit
and at least one bound, categorical values must be in the file's
vocabularies, no THA knee-ROM entry, no duplicates, every checkpoint day and a
long-term entry present for both procedures; `validate_sources=True` also
checks every `source_id` against its named corpus). `load_milestones()` is
the cached production loader. Test 19 checks every entry's passage id, URL
and quote fragments against the corpora and that a tampered copy is rejected.

`select_checkpoint(procedure, metric, day)` returns the nearest checkpoint
**at or before** the day; before day 7 it returns the day-7 entry (reported
as the target to work towards); after day 84 it returns the long-term entry
when the metric has one, otherwise the day-84 entry. `next_milestone()`
returns the next checkpoint day and its entries.

### 1b. Memory before asking (`agents/patient_memory.py`, extended)

`load_patient_memory()` now also returns `recent_metrics` (the `metrics`
rows of the last 7 days) and `request_rom` (the request's `current_rom`
text parsed into flexion/extension degrees by `parse_current_rom()`).
`PatientMemory.metric_series()` / `latest_metric()` give the per-day values
and the most recent one within N days. The agent loads memory once per
interview (cached on `RecoverySessionState`, same pattern as
`PainSessionState`) and:

- if flexion (or extension) was logged **today or yesterday**, it **confirms**
  the value instead of asking: *"Your log from yesterday says you could bend
  to 80° -- still about that?"* — "yes" stores the logged value, a number
  overrides it, "no" leads to the plain question, "I don't know" to the
  simpler rephrase; a value logged three days ago is asked afresh;
- a value the request already sent in `current_rom` is seeded as today's
  fact, fed back and never asked;
- when at least two values exist across the last week (including today's),
  the comparison ends with a trend: *"improving: 70 -> 80 -> 85"* (see 1i).

`write_today_metrics()` gained `rom_flexion`, `rom_extension` and
`exercise_completed` (the table already had the columns). Print prefixes
changed from `[PAIN][MEMORY]` to `[MEMORY]` since both agents share the module.

### 1c. Questions (`recovery_integration._ASK_QUESTIONS` / `_ALT_QUESTIONS`)

| Field | Question | Simpler rephrase (after "I don't know") |
|---|---|---|
| `rom_flexion_degrees` (TKA) | About how many degrees can you currently bend your knee? | Even a rough number helps -- when you sit and bend the knee back, roughly how many degrees would you say? |
| `rom_extension_degrees` (TKA) | Do you know your current knee extension measurement in degrees (how close to fully straight)? | **Can you get the knee fully flat on the bed?** → yes = 0°, "almost" = TKA-03's near-full 0–5°, no = beyond 5° |
| `mobility_status` (both) | How are you currently getting around -- walking independently, or using a walker, cane, or crutches? | Are you using anything to help you walk at the moment -- a frame, crutches or a stick -- or nothing? |
| `walking_duration_minutes` (both) | Roughly how many minutes can you walk at a stretch at the moment? | Roughly, can you walk for more than ten minutes at a time, or less than that? (→ the corpus's own ten-minute mark) |
| `stairs` (both) | How are you managing stairs -- not yet, one step at a time holding the rail, or foot over foot? | Have you tried stairs yet -- and if so, one step at a time or foot over foot? |
| `hip_precautions` (THA) | Are you still keeping to your hip precautions -- not bending the hip past a right angle, not crossing your legs, avoiding low chairs? | For example, are you avoiding bending the hip past 90 degrees and crossing your legs? |

THA asks walking aid → walking duration → stairs → hip precautions and never
knee ROM; TKA asks flexion → extension → walking aid → walking duration →
stairs. Daily activities, driving, return to work and "did my exercises" are
not asked but are extracted when volunteered and then compared too.

**One tracked question per turn; several answers accepted when volunteered**
(the existing `extract_and_apply` multi-slot pass, extended with the new
fields, bare/loose numbers for the pending numeric field, yes/no answers to
yes/no-shaped questions, and confirmation answers). A field is asked at most
twice (`MAX_ASKS_PER_FIELD`); after the second miss the agent says *"No
problem -- I'll leave flexion for now."* and asks about another metric.

### 1d. Assessment

Every collected value is compared with the nearest checkpoint at or before
the current day and the reply **names the checkpoint day in plain words**:
*"flexion of 85°, within the day-7 range of 70°-90°"* (the source passage id
goes into the result's `sources` metadata, never into the text -- see 1i).
Categorical values match / are "not yet at" / "beyond" the checkpoint; a
value answered as a range that straddles the stated range is reported as
*"may fall within ... -- a measured number would settle it"*; a words-only
checkpoint says *"the guidance gives no number, it expects ..."*; hip
precautions not being followed get *"please check with your surgical team"*.

- **Before day 7** the day-7 target is given as the thing to work towards
  (*"flexion of 60° on day 4; the first flexion checkpoint is day 7, which
  looks for 70°-90° -- the target to work towards"*) instead of "too early
  to compare".
- **After day 84** the long-term entry is used (*"the long-term guidance"*).
- **Never declines inside day 1-365.** The evidence gates (retrieved chunk
  must be TKA-03 / same procedure / parseable window / day inside the window)
  are gone; the file is the source. The only declines left are an
  unverifiable surgery date (the day cannot be placed; no LLM call either)
  and an unusable number ("That number doesn't look usable -- could you
  double-check and share it again?").
- A metric with no data is named in the final assessment (*"flexion: I don't
  have a value from you for this one, so I can't compare it."*).
- The **server-derived post-op day** is kept; when the client-sent
  `postop_day` disagrees, `recovery_integration.log_postop_day_mismatch()`
  logs a WARNING on the `agents.recovery` logger (and prints it), once per
  distinct disagreement per episode.

Mid-interview turns give one short clause per value just supplied and then
ask the one next question with a progress indicator (reusing
`pain_integration.progress_indicator`), all in one paragraph. The final
turn, when nothing is left to ask, produces the full block: *"Here's how
things compare on post-op day N, according to the discharge guidance:"* +
one line per metric (+ trend) + metrics with no data + *"Next milestone:
day 14 -- ..."* (at most two metrics) + *"Say 'recovery check' at day 14
and I'll compare."* ("recovery check" classifies as `recovery_progress`;
test 30.)

### 1e. Optional LLM explanation on the final turn

`ChatAgent.answer_question()` is called exactly once at the close with a
retrieval query built from the procedure, day and collected metrics (the
corpus's own vocabulary as hints), the deterministic block and the raw patient
message fenced as untrusted data in `domain_instruction`, and the abstention
sentence *"Whenever the discharge notes do not cover the question, say you
don't have that information and ask the patient to check with their surgeon
or physiotherapist."* The body is accepted only if it is non-empty, not
generic, free of trajectory language and names no number absent from the
block; otherwise the reply is deterministic only (engine
`Recovery Deterministic Assessment Engine`; with an accepted body the engine
is `Recovery Progress Agent - Grounded Assessment`). Interview turns never
call the LLM and no longer run a Recovery-owned RAG retrieval.

### 1f. Persistence

At the close only: `recovery_integration.persist_assessment()` writes the
collected flexion / extension / `exercise_completed` into today's `metrics`
row via `patient_memory.write_today_metrics()` (update in place or insert).
Only exact numbers are written — "fully flat" is the exact 0°, "nearly flat"
writes nothing for extension. Abandoned interviews persist nothing (test 29).

### 1g. State (`recovery_state.py`)

`RecoverySessionState` gained the cached memory snapshot
(`memory`/`set_memory`), the pending question's variant
(`pending_variant`: primary / alt / confirm) and confirm value
(`pending_confirm_value`), `note_confirm_declined()`,
`set_client_reported_postop_day()` and `last_mismatch_logged`. All are cleared
by the existing transient reset (day change / interview TTL). The public API
contract (facts only via `set_fact`, one pending field, day via
`apply_verified_day`/`clear_verified_day`) is unchanged.

### 1i. Readability pass (follow-up commit, `recovery_integration.py` + tests only)

Patient-facing text no longer contains passage ids (`TKA-03`,
`EV-TKA-REC-01`, ...) or the phrase *"the earlier Post-Op Day N
checkpoint"*. The ids stay in the result's `sources` metadata, which the
agent already collected from every `CheckpointResult` / `MilestoneEntry`
used; nothing in `specialized_agents.py` changed.

- **Checkpoint naming:** *"the day-7 range of 70°-90°"*, *"the day-21
  checkpoint"*, *"the long-term guidance"*; single bounds read *"the day-21
  mark of more than 10 minutes"* / *"the day-42 target of 0°"*.
- **Citation, at most once per reply, in plain words:** mid-interview, the
  first comparison of the turn carries *"(according to the discharge
  guidance)"*; the final block cites once in its header.
- **Mid-interview acknowledgements** are one short clause each
  (`comparison_clause()`): *"flexion of 85°, within the day-7 range of
  70°-90° (according to the discharge guidance), and improving: 70 -> 80 ->
  85"*, followed by the next question in the same paragraph.
- **Trend** (`trend_line()` now returns a `TrendNote`): *"improving: 70 ->
  80 -> 85"* when the last value has moved the right way for the metric
  since the first (flexion up, extension towards zero), *"steady: 80 -> 80"*
  when unchanged, otherwise the neutral *"over the week: 85 -> 80"*.
- **Final block** (`final_comparison_line()`): one line per metric that
  never repeats the acknowledgement sentence verbatim (*"flexion: 85° --
  within the day-7 range of 70°-90°; over the week 70 -> 80 -> 85,
  improving"*).
- **Next milestone** (`select_milestone_entries()`): at most the two metrics
  most relevant to the procedure and the next checkpoint day (TKA up to day
  21: flexion, extension; days 22-42: flexion, walking aid; THA up to day
  21: walking aid, walking duration; days 22-42: hip precautions, walking
  aid; both later: daily activities, driving; long term: return to work,
  daily activities), falling back to the metrics the interview collected.
  The full entry list still feeds `sources`.

Tests updated with a comment (same count, 93/93): 2, 3, 4, 7, 8, 12, 14,
18, 21, 23, 24, 26, 27 and 30 now pin the plain-words wording, assert that
no passage id or "earlier Post-Op Day" appears in any reply, that the
guidance is cited exactly once in the close, that the next-milestone
paragraph lists at most two metrics, and that the final line never equals
the acknowledgement clause.

## 2. Example conversations

### TKA, post-op day 10

Patient on record: `metrics` rows three days ago (flexion 70°, extension 8°)
and yesterday (flexion 80°, extension 5°). The client sent `postop_day=11`;
the surgery date derives day 10.

#### Before

**Patient:** How is my recovery going?

> About how many degrees can you currently bend your knee?

**Patient:** it's about 85 now

> Just circling back to this -- About how many degrees can you currently bend your knee?

**Patient:** I don't know the number

> Just circling back to this -- About how many degrees can you currently bend your knee?

**Patient:** almost, there's a small gap

> Just circling back to this -- About how many degrees can you currently bend your knee?

**Patient:** I'm using a cane and I can walk about 15 minutes

> Just circling back to this -- About how many degrees can you currently bend your knee?

**Patient:** one step at a time holding the rail

> Just circling back to this -- About how many degrees can you currently bend your knee?

(The old agent read nothing from the record, did not understand a number
without the word "degrees", did not count "I don't know the number" as a
miss, and had no walking, duration or stairs questions; it would have kept
asking the same question indefinitely.)

#### After

**Patient:** How is my recovery going?

> Let's see where you are on post-op day 10. Your log from yesterday says you could bend to 80° -- still about that? (a few more questions)

**Patient:** it's about 85 now

> Thanks for sharing that -- flexion of 85°, within the day-7 range of 70°-90° (according to the discharge guidance), and improving: 70 -> 80 -> 85. Your log from yesterday says your extension was 5° -- still about that? (a few more questions)

**Patient:** I don't know the number

> That's okay. Can you get the knee fully flat on the bed? (a few more questions)

**Patient:** almost, there's a small gap

> Thanks for sharing that -- extension (nearly flat), within the day-7 range of 0°-5° (according to the discharge guidance), and improving: 8 -> 5. How are you currently getting around -- walking independently, or using a walker, cane, or crutches? (one or two more questions)

**Patient:** I'm using a cane and I can walk about 15 minutes

> Okay -- walking aid: a cane, matches the day-7 checkpoint (according to the discharge guidance): walking with a frame, crutches or cane on a level surface. walking duration: 15 minutes; the day-7 guidance gives no number, it expects walking little and often around the home. How are you managing stairs -- not yet, one step at a time holding the rail, or foot over foot? (last question)

**Patient:** one step at a time holding the rail

> All five things we checked are within the expected range or as described for your stage, and flexion and extension are improving over the week.
> Here's how things compare on post-op day 10, according to the discharge guidance:
> - flexion: 85° -- within the day-7 range of 70°-90°; over the week 70 -> 80 -> 85, improving
> - extension: nearly flat -- within the day-7 range of 0°-5°; over the week 8 -> 5, improving
> - walking aid: a cane -- as the day-7 checkpoint describes (walking with a frame, crutches or cane on a level surface)
> - walking duration: 15 minutes -- no number in the day-7 guidance; it expects walking little and often around the home
> - stairs: one step at a time -- as the day-7 checkpoint describes (managing two or three steps up and down with your aid)
>
> Next milestone: day 14 -- flexion: about 80 degrees or more of active bending, improving week by week; extension: straightening to within 10 degrees of fully straight. Say 'recovery check' at day 14 and I'll compare.

Sources metadata on the final turn (never in the text): `TKA-03`,
`EV-TKA-REC-01`, `EV-TKA-REHAB-02`, `EV-TKA-REC-02`, `EV-TKA-REHAB-03`.

Logged once on the first turn:

## 3. Shared changes needed (outside this branch's scope)

1. **`agents/agent_router.py` — forward `current_rom` to the Recovery agent.**
   `RecoveryProgressAgent.handle()` now accepts `current_rom`, but the router
   only forwards it to `RehabilitationAgent`; Recovery is dispatched through
   the generic branch. One line in the generic dispatch (or a dedicated
   Recovery branch like Pain's) makes the request field reach the agent; until
   then it only works for direct callers and tests.
2. **`lam/orchestrator.py` — pass the Recovery state's pending variant through
   the continuation check.** `check_recovery_continuation()` reads the variant
   and confirm value from the state itself, so no change is required for
   correctness; but the orchestrator's `_has_active_pain_followup` still runs
   first, so a bare "yes" during a Recovery confirmation while a Pain question
   is also pending goes to Pain. Deciding the precedence belongs to the
   orchestrator.
3. **`agents/chat_agent.py` — token budget for the final turn** (same item as
   the Pain rework): `answer_question(..., max_tokens=None)` would let the
   Recovery close ask for a short explanation explicitly.
4. **`patient_database.py` — a first-class metrics upsert.**
   `patient_memory.write_today_metrics()` still writes the `metrics` table with
   its own SQL through `connection_scope()`; an `upsert_daily_metrics()` helper
   there would be the proper home now that two agents use it.
5. **Intent classifier:** the check-in offer depends on "recovery check" being
   classified as `recovery_progress` (verified by test 30 via the "recovery"
   keyword). Keep "recovery" in that keyword set if the classifier is retuned.
   Note also that fresh (non-continuation) classification of "I can do stairs
   one at a time" is `daily_activity` and of "I still use a walker and can
   walk 10 minutes" is `rehabilitation`; both reach Recovery today only through
   the continuation hook while a Recovery question is pending.
6. **Flutter client / `ChatRequest`:** `postop_day` disagreements are now
   logged server-side; the client could stop sending its own count and rely on
   `surgery_date`, or the API could return the server-derived day.
7. **Timezone:** unchanged accepted limitation — the server's local calendar
   date is "today" for both the post-op day and the `metrics.date` key (see the
   convention block in `recovery_integration.py`).
